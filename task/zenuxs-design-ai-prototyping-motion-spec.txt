ZENUXS DESIGN — AI-NATIVE PROTOTYPING + MOTION ENGINEERING SPECIFICATION
======================================================================

PURPOSE
-------
This document is an engineering specification for the AI/coding agent working on
Zenuxs Design.

The goal is to extend the existing Zenuxs Design / OpenPencil-based editor so
that it can create not only static UI designs, but also interactive prototypes,
screen flows, states, transitions, micro-interactions, and motion/animation
behaviors.

IMPORTANT:
We are NOT trying to replace the existing Zenuxs/OpenPencil foundation.
We are extending it.

The existing editor, scene graph, renderer, design operations, AI tools, file
formats, and working functionality must be preserved unless a change is
strictly required.

The desired end state is:

    User describes a UI/UX experience
              ↓
    AI understands what kind of experience it is
              ↓
    AI selects the appropriate design + prototype + motion primitives
              ↓
    Zenuxs stores those primitives as real editable document data
              ↓
    Designer can inspect/edit them
              ↓
    Preview mode actually runs the interactions/motion
              ↓
    Save/reopen/import/export preserve the behavior
              ↓
    AI can understand and modify the same behavior later

This is NOT a request to simply install an animation library and call it done.

1. CURRENT ZENUXS / OPENPENCIL FOUNDATION
======================================================================

Zenuxs Design is based on an OpenPencil fork.

Current upstream/reference:
https://github.com/open-pencil/open-pencil

Zenuxs project:
https://github.com/developer-rs5/zenuxs-desigen
https://github.com/developer-rs5/zenuxs-desigen.git

OpenPencil's core architectural idea is important:

    A design is a node tree / editable document model,
    and editor, CLI, SDK, MCP and AI operations work against the same
    underlying document/operation model.

The existing ecosystem includes, among other things:

- scene graph / nodes
- frames
- text
- shapes
- images
- components
- variants
- variables/design data
- auto layout
- CSS Grid
- .fig / .pen handling
- rendering
- editor operations
- AI tools
- MCP
- CLI
- Vue SDK
- design-to-code / code-to-design capabilities

DO NOT rebuild these capabilities.

The purpose of this project is to add a native interaction/prototyping/motion
layer on top of the existing design model.

2.3 XState — STATE MACHINE / INTERACTION LOGIC REFERENCE
----------------------------------------------------------------------

Repository:
https://github.com/statelyai/xstate

What it is:
A JavaScript/TypeScript state-management and orchestration system based on
state machines, statecharts, actors, and event-driven logic.

Why it matters:
Many "animations" users request are actually visual transitions between
states.

Examples:

    Login
      idle
      ↓ submit
      loading
      ↓ success
      home

    Button
      default
      ↓ hover
      hover
      ↓ press
      pressed
      ↓ release
      default

    Modal
      closed
      ↓ open
      entering
      ↓ transition complete
      open
      ↓ close
      exiting
      ↓
      closed

Study:

- state definitions
- transitions
- events
- guards/conditions
- actions
- deterministic state changes
- serialization ideas
- visualization/debugging ideas

Do not automatically install XState as a required runtime dependency.

First determine whether a smaller Zenuxs-native state model is better.

The important thing is to adopt the CONCEPTUAL MODEL where useful.

2.4 Motion for Vue / Motion-V — MOTION PRIMITIVE REFERENCE
----------------------------------------------------------------------

Repository:
https://github.com/motiondivision/motion-vue

What it is:
An open-source production animation library for Vue. It provides primitives
such as:

- springs
- keyframes
- layout animations
- gestures
- hover/tap/drag behavior
- exit animations
- scroll animations
- orchestration
- transforms
- easing-related capabilities

License:
The repository describes Motion for Vue as MIT licensed.

Why study it:
It is a useful reference for how modern motion APIs express animation intent.

IMPORTANT ARCHITECTURE CONSTRAINT:

Zenuxs uses a design-editor/scene-graph renderer rather than simply being a
DOM application.

Therefore:

    DO NOT assume that <motion.div> is the correct implementation model
    for the Zenuxs editor canvas.

Instead study:

- motion semantics
- interpolation
- spring behavior
- keyframes
- orchestration
- gesture concepts
- enter/exit behavior

Then implement equivalent concepts against Zenuxs' own scene graph and renderer.

The Zenuxs document should describe motion.
The Zenuxs runtime should evaluate motion.
The renderer should render the current evaluated state.

======================================================================

The target system should have FOUR related but separate layers.

----------------------------------------------------------------------

Keep the current design model:

- pages
- frames
- groups
- text
- images
- vectors
- components
- instances
- variants
- variables
- layout
- visual properties

No unnecessary rewrite.

----------------------------------------------------------------------

Add a native structured model representing interaction behavior.

Conceptually:

    PrototypeFlow
    Interaction
    Trigger
    Condition
    Action
    Target
    Transition

Examples:

    OnClick
        → NavigateTo
        → Home
        → SlideLeft

    OnClick
        → OpenOverlay

    Hover
        → SetVariant
        → Button
        → Hover

        → UpdateState
        → Drawer
        → x-position

The exact TypeScript/database schema must be designed after inspecting the
existing document architecture.

Do not blindly use these exact names if the project already has conventions.

----------------------------------------------------------------------

Represent interactive state where required.

Examples:

    default
    hover
    pressed
    focused
    disabled
    loading
    success
    error
    open
    closed
    expanded
    collapsed

A state should be data that can be understood by both:

- the editor
- the AI

The state model must be deterministic and serializable.

Possible primitives:

    animation
    keyframes

    delay
    easing
    spring
    iteration
    direction

    sequence

Property targets could include:

    opacity
    rotation
    scale
    fill/color
    stroke
    corner radius
    blur/effects
    clip/mask values
    component state/variant
    visibility

    keyframe animation

and:

    spring-based animation

The exact model must remain compatible with the scene graph.


======================================================================
4. PROTOTYPE VS MOTION — KEEP THE CONCEPTS DISTINCT
======================================================================

The AI must understand:

    Prototype interaction
        answers:
        "What happens when the user does something?"

    Motion
        answers:
        "How does a visual change happen over time?"

Examples:

    Tap button
        = trigger

    Navigate to Home
        = action

    Slide left
        = transition

    400ms ease-out
        = motion timing

    Spring open
        = motion model

Do not collapse all of these into a single "animation" object.

Similarly:

    Variant change
    ≠ Page navigation

    Component state
    ≠ Prototype flow

    Motion
    ≠ State machine

The architecture should allow them to work together.


======================================================================
5. WHAT THE AI MUST UNDERSTAND
======================================================================

The AI must become intent-aware.

Users should NOT have to understand the internal model.

If the user says:

"Make a splash screen that fades into the home screen."

The AI should infer something like:

    two screens
    splash
    home
    trigger = load/start
    action = navigate
    transition = fade
    duration = sensible default
    easing = sensible default

If the user says:

"Make this button feel pressable."

The AI should infer:

    interaction = pointer/tap
    states = default / pressed
    visual state change
    motion = small scale/position/effect
    fast spring or easing

If the user says:

"Create a login flow with loading and error states."

The AI should infer:

    state model
    idle
    loading
    success
    error

    events:
    submit
    success
    failure

    visual transitions between states

If the user says:

"Build an onboarding flow where the cards slide between steps."

The AI should infer:

    multiple screens/frames
    flow
    next/previous actions
    transition
    horizontal motion
    progress state

The AI must choose the appropriate Zenuxs primitives automatically.

7. EDITOR UX REQUIREMENTS
======================================================================

A designer must be able to inspect and edit prototype/motion behavior.

Do not hide the behavior completely inside AI-generated metadata.

The editor should eventually expose appropriate UX such as:

    Prototype / Interactions panel
    Motion / Animation panel
    State / Variant editing
    Preview / Present mode
    Timeline where needed

The exact UI should fit the existing Zenuxs Design system.

Do not start by building a giant complex timeline if a smaller inspector-driven
motion editor is enough for the first implementation.

Build the smallest coherent foundation first.


======================================================================
8. PREVIEW / RUNTIME
======================================================================

The editor and runtime should be conceptually separate.

EDIT MODE:
    inspect
    modify
    configure
    select
    keyframe
    connect interactions

PREVIEW MODE:
    user clicks/taps
    events fire
    state changes
    prototype actions execute
    transitions run
    motion is evaluated
    screen changes
    overlays open/close

The exact same saved document should drive both.

Do not create one fake preview representation that differs from the actual
editable design model.


======================================================================
9. SAVE / LOAD / DATABASE REQUIREMENTS
======================================================================

Zenuxs now has a connected backend/database.

Prototype and motion information must eventually survive persistence.

Minimum expectation:

    Create interaction
        ↓
    Save
        ↓
    Refresh/reopen
        ↓
    Interaction still exists

Likewise:

    Create animation
        ↓
    Save
        ↓
    Reopen
        ↓
    Animation still exists

Database persistence must not be implemented as a disconnected shadow system.

If behavior belongs in the design document, it should remain document data.

If server-side project metadata is required, keep that clearly separate.

Test:

    editor state
    serialized document
    database record
    reload
    deserialization
    runtime behavior

All must agree.

    depend on arbitrary timers

16. AI TOOL DESIGN
======================================================================

The AI must not be forced to express everything through low-level generic
node operations.

Add higher-level semantic operations where appropriate.

Examples:

    createPrototypeFlow
    createInteraction
    setInteractionTrigger
    setInteractionAction
    setTransition
    createState
    setState
    createAnimation
    addKeyframe
    setSpring
    setEasing
    createOverlayBehavior
    connectScreens
    previewPrototype

These higher-level operations should internally use the same validated,
undoable document mutation system as the rest of the editor.

The goal is:

    AI semantic intent
        ↓
    validated Zenuxs operation
        ↓
    document mutation
        ↓
    renderer/runtime
        ↓
    saved document

Not:

    AI invents arbitrary JavaScript
        ↓
    hidden side effect
        ↓
    uneditable behavior

17. AI MUST VALIDATE ITS OWN WORK
======================================================================

After generating prototype/motion behavior, AI should verify:

- referenced targets exist
- destination pages exist

- state names are valid
- variants exist

======================================================================
23. VERSIONING / MIGRATIONS
======================================================================

Prototype and motion data may become part of persisted design documents.

Design the model with future evolution in mind.

Prefer:

    versioned schema
    explicit defaults
    migrations
    backwards-compatible reads
    graceful handling of unknown optional fields

Avoid:

    unversioned arbitrary blobs
    provider-specific data as document truth
    impossible-to-migrate structures
    breaking all previous documents for one feature


======================================================================
24. PERFORMANCE
======================================================================

Motion and interaction should not make the editor sluggish.

Be especially careful with:

- large node trees
- many keyframes
- many simultaneous animations
- continuous pointer events
- drag gestures
- scroll-linked effects
- springs
- repeated render loops
- preview transitions
- event listener counts

Prefer:

    event-driven updates
    bounded work
    requestAnimationFrame where appropriate
    memoized/static data
    clean listener lifecycle
    incremental updates

Do not animate the entire scene graph when only one target changes.


======================================================================
25. ERROR / CANCELLATION BEHAVIOR
======================================================================

AI generation can stop.
Network requests can fail.
Operations can fail.
Targets can disappear.

The runtime must fail gracefully.

Examples:

    AI stop
        → stop active generation
        → do not corrupt document

    target deleted
        → interaction becomes invalid/clearly reported
        → no runtime crash

    malformed animation
        → validation error
        → no infinite loop

    missing destination
        → clear error
        → editor remains usable


======================================================================
26. HUMAN-LIKE TESTING REQUIREMENT
======================================================================

When the feature is implemented, use the product like a real designer.

Do not test only by calling internal functions.

Examples:

    "Create a mobile onboarding flow."

    ask AI to modify it

======================================================================
27. SECURITY / TRUST BOUNDARIES
======================================================================

Do not allow AI-generated behavior to bypass editor validation.

AI actions must pass through the same:

    validation
    permission
    document mutation
    undo/redo
    persistence

rules as normal editor actions.

Do not execute arbitrary generated JavaScript inside the editor as the primary
implementation of prototype/motion behavior.

If code execution is eventually supported for advanced exports, sandbox and
separate it clearly from the editable document model.


======================================================================
28. WHAT "DONE" MEANS
======================================================================

This work is NOT done because:

- a motion library was installed
- a prototype panel exists
- a button says "Preview"
- AI generated an animation-like result
- one demo works
- TypeScript compiles

It is done only when:

1. The underlying model exists.
2. The editor can create/edit it.
3. AI can create/edit it.
4. Preview executes it.
5. The behavior is saved.
6. The behavior survives reload.
7. Invalid structures are rejected safely.
8. Existing editor functionality still works.
9. AI still works.
10. Database persistence works where applicable.
11. Console/network/server errors are clean.
12. Multiple independent test rounds pass.
13. Real user-like flows work.
14. The feature is extensible without redesigning the whole architecture.

======================================================================
30. FINAL PRODUCT VISION
======================================================================

The final Zenuxs Design experience should let a user say things like:

    "Make a modern SaaS landing page."

    "Create a mobile onboarding flow."

    "Add a splash screen that fades into the home screen."

    "Make the button feel interactive."

    "Add a bottom sheet that springs up."

    "Create loading, success and error states."

    "Make this modal slide from the bottom."

    "Make the cards swipe horizontally."

    "Add a subtle hover animation."

    "Turn this static mockup into an interactive prototype."

And the AI should understand:

    what needs to be designed
    what needs to be a state
    what needs to be an interaction
    what needs to be a transition
    what needs to be a motion
    which Zenuxs primitives represent it
    how to build it
    how to validate it
    how to save it
    how to preview it
    how to modify it later

The result should remain:

    EDITABLE
    STRUCTURED
    SERIALIZABLE
    PREVIEWABLE
    AI-MODIFIABLE
    TESTABLE
    PERSISTENT
    EXTENSIBLE

The core principle is:

    LEARN FROM EXISTING OPEN-SOURCE SYSTEMS.
    DO NOT BLINDLY DEPEND ON THEM.
    BUILD THE RIGHT ZENUXS-NATIVE MODEL.

And the final test is not:

    "Did we implement the feature?"

The final test is:

    "Can a real user ask for an interactive animated UI,
     can Zenuxs actually build it,
     can the user see/preview it,
     can they edit it,
     can it be saved and reopened,
     can AI understand it later,
     and do all existing features still work?"

Only then consider the work complete.
